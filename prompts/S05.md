# S05 Shell-user feasibility spike

Depends on: S03. Branch: step/S05-<name>.

Goal: Prove which parts of the server run as the ADB shell user on real devices before building launchers around it.

## Prompt 5A: tooling and probe

```text
Follow AGENTS.md. Step S05A, branch step/S05a-spike. Work in :server-core and tools/spike. Read docs/findings.md (SEC-04, CQ-03).

1. Add CapabilityProbe in :server-core that attempts, one by one: create the mirror virtual display, inject a harmless input event, expand and collapse the notification shade, read and set rotation, set display power on and off, send KEYCODE_WAKEUP, set and read the clipboard. Each returns Supported, Unsupported(reason) or Denied(permission). Print one JSON line per capability.
2. Add a FakeContext (package com.android.shell, uid-aware) for hidden APIs that need a Context identity, in a platform/ package behind an interface. No UI library or app Context may be used in :server-core.
3. Add tools/spike/run-shell-server.sh and run-shell-server.ps1: build :server-core as a dex jar, adb push to /data/local/tmp/velocast-server.jar, run it with app_process as the shell user using CLASSPATH, run the probe, pull the output into tools/spike/results/<model>-android<api>.json and print a summary table.
4. Add tools/spike/README.md with prerequisites (USB or wireless debugging, authorised computer) and a table template for the owner.
Do not change production behaviour. Definition of done: the scripts work against an emulator or a device you can reach; unit tests cover the probe's result mapping; summary per AGENTS.md.
```

## Prompt 5B: interpret results (after the owner runs the devices)

```text
Follow AGENTS.md. Step S05B, branch step/S05b-spike-results. The owner has added JSON results under tools/spike/results/ (and pasted raw logs below).
1. Build the capability matrix (rows: capability; columns: device and Android version) and write docs/spike-shell-user.md including causes of every failure.
2. For each failure decide: fix in code (for example missing FakeContext identity, wrong reflection signature for that API level), downgrade to a typed ERROR or capability flag, or document as a ROM limitation (for example input injection needing an OEM toggle).
3. Implement the fixes inside the platform/ shims with per-API-level handling and tests where possible. Make the server report capabilities to the viewer through STATUS.
4. Update docs/architecture.md and the findings traceability with what was learned.
Raw logs from the owner:
<paste logs here>
Definition of done: the server completes a full session as the shell user on every device in the matrix that supports it; remaining gaps are documented with user-facing errors; summary per AGENTS.md.
```

## Acceptance criteria

- Capability matrix covers at least Android 11, 13, 14, 16 and one Xiaomi or Samsung ROM.
- Every failure has a documented cause and either a fix or a typed error.
- The server runs unprivileged-by-root on the reference old phone.

## Owner checks

- Run tools/spike/run-shell-server.sh on the devices listed in the matrix and paste the output into the PR or the follow-up prompt.
